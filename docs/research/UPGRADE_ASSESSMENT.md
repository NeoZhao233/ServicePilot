# ServicePilot 动态规划与安全恢复方案评估

评估日期：2026-09-24。范围：审查用户提供的升级方案，读取现有实现，运行原有测试和隔离故障探针。未实施架构升级，未调用真实退款或在线模型。

## 结论

建议采纳目标与渐进式原则，但调整实施顺序和实验设计。最急需的是可靠业务执行边界、授权绑定与持久化；目前尚无证据证明四类问题需要 LLM 生成通用 DAG 才能解决。先建立确定性任务状态机作为强基线，再验证动态规划的增量价值。

方案优点：业务事实优先、未知结果不盲目重试、简单请求走原路径、预算约束、保留安全基线、不强行引入知识图谱/多 Agent/长期记忆。这些原则与项目相符。

复现：从 servicepilot 目录执行 `PYTHONPATH=src .venv/bin/python docs/research/assessment_probe.py`。脚本输出观察结果，不是用于宣布升级验收通过的断言测试。

现有业务没有退款数据库，因此不能伪称这些场景已验证数据库最终状态。本次检查的是原实现的权威内存记录。后续增加业务数据库后，必须补上重启、并发、事务中断、跨进程重放及数据库终态断言。原方案“未签收时制定退款计划”也应调整：当前规则拒绝未签收退款；应分别测试从不可办变为可办，以及检查后从可办变为不可办。

## 四篇论文的适配判断

已获取四篇论文 arXiv v1 HTML，核对核心方法/算法及部分实验内容，并打开 AgentDebug、AgentSpec 官方仓库页面。没有运行论文代码，也未逐文件审计核心实现；这不是完成版论文复现或完整研究交付。

- [ReflAct](https://arxiv.org/html/2505.15182v1)：以目标和观察支撑反思、指导下一行动，实验在 ALFWorld、ScienceWorld、Jericho。适合借鉴目标与事实差异检查。当前退款资格规则和结果检查已有局部对应；将其扩展为数据库谓词、目标版本和完成条件属于工程设计，不能说是论文原生提供的事务协议。
- [ReasonPlanner](https://arxiv.org/html/2410.09252v1)：时序世界模型、预测轨迹及基于执行差异的修订。可借鉴观察时间和状态变化驱动重规划，不应照搬知识图谱与预测环境模型。项目尚无订单版本和任务依赖；基于订单事件的任务计划是适配方案，而非复现原算法。
- [AgentDebug](https://arxiv.org/html/2509.25370v1)：按模块分析轨迹、定位关键错误并针对性反馈、重新 rollout。适合错误分类和定位；当前只有通用重试。错误码、unknown 状态、对账及重试预算是业务工程设计。真实退款不能像可重置的评测环境那样从出错步骤重新执行。其诊断和恢复实验不能证明支付幂等性。
- [AgentSpec](https://arxiv.org/html/2503.18666v1)：trigger/check/enforce 的运行时约束，考察跨域效果与运行开销。可借鉴统一执行入口上的确定性谓词。现有白名单、归属校验和 MCP 确认检查可复用；事务、唯一键与授权凭证并不是其规则框架自动赋予的保障。不需要为本项目另造 DSL。

[AgentDebug 官方仓库](https://github.com/ulab-uiuc/AgentDebug)；[AgentSpec 官方仓库](https://github.com/haoyuwang99/AgentSpec)。论文实验与电商售后的环境、工具和风险不同，不能迁移论文提升百分比作为项目预期。

## 方案必须补全的设计

1. **先安全底座，再扩大自主执行。** 原第五阶段应提前：统一业务服务、持久化操作账本、授权和版本、执行结果查询，是恢复与规划的前置依赖。不能上线 B2/B3 后才补幂等保障。
2. **统一所有入口。** 本地 Agent、旧流程与 MCP 共用同一个业务执行服务和权威仓库；只保护 MCP 路径会漏掉现有主流程。旧路径回退也不能绕过新安全边界。
3. **原子校验与写入。** “执行前再查询”仍有检查后状态改变的窗口。本地模拟需要在一个事务内比对订单版本、权限、授权和唯一操作并写入；远端需要服务端条件写入与幂等协议。本地锁不能替代远端承诺。
4. **区分业务操作与调用尝试。** operation_id 在首次提交前持久化，同一操作跨重试/重规划保持不变；attempt_id 每次调用变化。目标改变不能靠换幂等键重新提交旧操作。先定义全额退款、部分退款和换货的业务互斥关系，不能永远只按订单号去重。
5. **明确授权模型。** 保存可信 actor、订单、操作、金额/币种、业务版本、目标/计划版本、有效期及一次性消费状态；不能让模型生成或扩大授权。金额应使用整数分或 Decimal。仅改变日志等无关信息是否失效，需要明确版本粒度，避免反复确认。
6. **给未知结果独立状态。** 建议 prepared → submitted → succeeded / failed / unknown；unknown → reconciling → 已确认终态或人工处理。查询不到不一定等于没执行，需明确服务端查询一致性。先对账、再决定是否重试，不能把“已成功但丢响应”当作最初即可准确知道的错误类别。
7. **定义跨轮与并发语义。** 同一会话如何映射多个订单/任务？新消息如何打断运行中的计划？建议目标更新、任务版本比较更新和写入执行建立明确顺序；一旦提交完成，后来的取消只能进入后续售后流程。Checkpoint 不等于退款账本，不可通过图恢复重放写操作。
8. **限制计划表达能力。** PlanStep 还需参数、工具版本、操作标识、结果引用；前置条件与 expected_effect 用受限类型化谓词，不允许自然语言直接变成执行代码。检查 DAG 之外还需校验输出引用、权限及数据来源。completed/pending 尽量从步骤状态派生，避免重复存储失配。
9. **收紧完成条件与范围。** 当前换货只能以“核验工单已创建”为完成，不能标为“已完成换货”；退款申请成功也不同于款项到账。建议首期仅覆盖退款与换货受理任务。
10. **真实人工接管。** 给 escalation 持久化原因、操作 ID 和待对账状态；不只是生成“转人工”回复。

## 推荐实施与验证顺序

- 阶段 A：冻结原样基线，修复目标覆盖问题，定义业务服务协议和权威身份。
- 阶段 B：建立持久化业务模拟器、操作账本、绑定授权与条件写入；所有入口复用。验收超时、重复请求、并发、崩溃重启。
- 阶段 C：增加轻量任务状态和确定性恢复状态机，复用查询结果时检查版本和来源；按结构化目标判定完成。
- 阶段 D：在现有 graph_runtime 中加入受限规划子图，只让复杂请求进入；先模板计划，再加入 DeepSeek 候选计划生成。重规划、调用和失败预算持久化。
- 阶段 E：冻结模型/数据/故障脚本，运行多次对照，报告成功率、违规次数、成本、延迟分布和人工接管。

保留用户 B0–B4 作为隔离实验，但增加关键强基线：**原工作流 + 新安全底座 + 确定性恢复，不使用 LLM 规划**。只有与它相比有收益，才能把提升归因于规划，而非基础事务修复。各组使用相同业务后端、故障时点和模型预算；安全消融只在隔离模拟器中运行。简单查询也应纳入，衡量新增架构的回归与额外开销。

本次证据支持“需要升级可靠执行与任务状态”；尚不足以支持“必须由 LLM 规划”或任何性能提升比例。最终建议：方案方向通过，补全以上契约并调整顺序后实施。
